# Building

Related: [platforms](platforms.md) · [releases](releases.md) · [dependencies](dependencies.md)

**Status: there is no Rust workspace yet.** Phase 1 of the [roadmap](roadmap.md) creates it. The commands below
are the contract that Phase 1 must satisfy; they are written now so that the first pull request has a target
rather than an improvisation.

Building the **C++ reference** program is a different matter and is documented in §7 — it works today, because
`legacy/` contains a complete program.

---

## 1. Requirements

| Requirement | Version | Notes |
| --- | --- | --- |
| Rust | 1.85 or newer | `rustup` is the expected way to install it |
| Cargo | shipped with Rust | |
| A C compiler | **not required** | pure-Rust TLS and compression ([dependencies](dependencies.md) §2.6, §2.7); a C compiler appearing in the build is a defect |
| Network at build time | **not required** | `cargo build --offline` must work from a warm cache |
| System Qt / GTK / OpenSSL | **not required** | Slint draws its own widgets |

Nothing else. If a platform needs more, this table is wrong and the pull request that discovers it fixes the
table.

## 2. Development build

```sh
git clone https://github.com/RUdolf1517/Morid
cd Morid
cargo build                  # debug: fast to compile, slow to run, large
cargo build --release        # what users get
cargo test                   # unit, fixture and integration tests
cargo run --bin morid -- list https://example.test/v/abc
cargo run --bin morid-gui
```

Checks required before a pull request is reviewable ([CONTRIBUTING](../CONTRIBUTING.md) §2):

```sh
cargo fmt --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-features
cargo deny check
cargo audit
```

## 3. Workspace layout

```
Cargo.toml            workspace members and shared profiles
crates/morid-core     domain types, no I/O
crates/morid-ext      extension schema
crates/morid-engine   process spawning and output parsing
crates/morid-store    settings and data files
crates/morid-net      HTTP, hashes, unpacking
crates/morid          service layer: queue, jobs, argv construction (library)
crates/morid-cli      `morid` binary: argument parsing, exit codes, output
crates/morid-gui      Slint UI + `morid-gui` binary
ui/                   .slint files
xtask/                build, size measurement, packaging helpers
```

The exact content of each manifest — workspace members, `[workspace.package]`, pinned dependency versions,
`[profile.release]`, `rust-toolchain.toml`, `deny.toml` — is written out in
[workspace-manifest.md](workspace-manifest.md). That file is a specification: none of it exists yet.

Release profile is fixed at the workspace level:

```toml
[profile.release]
opt-level = "s"
lto = "fat"
codegen-units = 1
panic = "abort"
strip = "symbols"
```

Rationale: the project values size ([D-008](decisions.md)); `panic = "abort"` is acceptable because a panic in a
download manager is a bug, not a recoverable condition, and there is no `catch_unwind` in the design. The cost —
no unwinding for recovery — is stated here so it is not rediscovered later.

## 4. Size measurement

The release binaries are measured and reported, not gated ([D-008](decisions.md)):

```sh
cargo build --release
ls -l target/release/morid target/release/morid-gui
cargo bloat --release --crates      # what the size is made of, when it grows unexpectedly
```

The numbers go into the pull request and into the history table in [dependencies](dependencies.md) §6. A growth
of more than 10 % needs an explanation in the description.

## 5. Cross-compilation

Only one direction is supported: **Linux x86_64 → Linux aarch64**.

```sh
rustup target add aarch64-unknown-linux-gnu
cargo build --release --target aarch64-unknown-linux-gnu
```

Requires a cross linker (`aarch64-linux-gnu-gcc` for linking) — the *build* has no C sources, but `cc` is still
used as the linker driver. CI does this in a container to keep the toolchain pinned.

macOS and Windows artefacts are built on their own runners ([platforms](platforms.md) §3). Cross-compiling to
Windows from Linux is not supported and not documented: an untested cross build is worse than no build.

## 6. Packaging

| Artefact | How | Notes |
| --- | --- | --- |
| Linux `.tar.gz` | `xtask dist` | contains `morid`, `morid-gui`, `extensions/`, licences, `docs/` |
| Linux `.deb` | `cargo-deb` or a hand-written control file | depends on libc only |
| Flatpak | manifest in `packaging/flatpak/` | the original's manifest in `legacy/src/flatpak/` is the starting point, minus the deno workarounds |
| macOS `.app` + `.dmg` | `xtask bundle-macos` | `Info.plist` from `packaging/macos/` |
| Windows installer | Inno Setup script generated by `xtask` | per-user install, no admin prompt |
| Windows portable `.zip` | `xtask dist` | data beside the executable ([data-compat](data-compat.md) §1) |

Backend binaries (yt-dlp and friends) are **not** bundled. The installer may offer to fetch them on first run,
from their own release pages ([D-014](decisions.md)), with size and SHA-256 verification. A packager who bundles
them does so under their licences ([THIRD-PARTY](../THIRD-PARTY.md) §3).

## 7. Building the C++ reference

`legacy/` is the original C++/Qt program, kept permanently as the behavioural reference ([D-015](decisions.md)).
It is **not** the product and it is not built by the root build.

```sh
cd legacy
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release          # Qt6
cmake -S . -B build -DBUILD_WITH_QT6=OFF                # Qt5, if that is what you have
cmake --build build -j
./build/media-downloader
```

Requires Qt5 or Qt6 with Core, Widgets and Network, plus CMake 3.26 or newer (the project accepts older CMake
with reduced guarantees). One known breakage from the move: `CMakeLists.txt` copies `changelog` into the macOS
bundle, and that file is now `../CHANGELOG-legacy.md`. A macOS bundle build needs a local, uncommitted adjustment,
recorded in [../legacy/removed-ci-workflows.md](../legacy/removed-ci-workflows.md). On Windows the original's `legacy/build_windows.ps1` encodes the maintainer's local
paths and will need editing — it is a record of how the original was built, not a script for a stranger.

Why you would build it: to capture a golden fixture ([testing](testing.md) §4), or to compare behaviour on a
disputed case. Why you would not: it is not maintained, receives no security fixes, and nothing that is fixed
there flows into Morid.

## 8. Reproducibility

- `Cargo.lock` is committed; a build from a clean checkout resolves the same versions.
- The build does not fetch anything: no `build.rs` downloads, no git dependencies by branch, no `include_bytes!`
  of a downloaded artefact ([dependencies](dependencies.md) §1).
- Byte-identical artefacts across machines are not promised — different Rust versions and linkers produce
  different binaries. The promise is "same inputs, same behaviour", and the release notes state the exact
  toolchain used.
